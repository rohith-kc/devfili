# DevFili decisions log

Format: decision, why, date.

## Phase 2

- **Dropped the `zod-to-json-schema` dependency; use zod v4's native `z.toJSONSchema()` instead.** Tested directly: against our installed `zod@4.6.7`, `zod-to-json-schema@3.25.2` silently produces an empty schema (`{"$schema": "..."}`, no `properties`, no `required`) because it reads zod v3's internal `_def` shape, which v4 no longer has. `z.toJSONSchema()` produces the correct shape and - for a plain `z.object()` - already sets `additionalProperties: false`, exactly what Groq's `json_schema: {strict: true}` mode needs for `DraftCore`/`DraftPath`. (2026-10-24)

- **`verdict.gates.customerAdmin` (and `tile.customerAdmin`) is derived by code from `DraftCore.facts.customerAdminLikely`, overriding whatever `DraftPath.gates.customerAdmin.applies` the model drafted.** `docs/SPEC.md` section 7 (`tier.ts`) is explicit that this gate state "comes from `facts.customerAdminLikely`", which is a code-decides rule consistent with `CLAUDE.md`'s "the model never decides ... difficulty tier ... Code does." But `docs/PROMPTS.md` P4 also has the model draft its own `gates.customerAdmin.applies` independently, which could disagree with the fact. Finalize keeps the model's `who`/`what` prose and claims for that gate (descriptive text, not a yes/no/unknown decision) but always recomputes `applies` from the fact. (2026-10-24)

- **Turned off `cacheComponents`/`partialPrefetching` in `next.config.ts`** (both scaffolded `true` by default by this Next.js 16.4.3 create-next-app template). "Cache Components" makes `export const runtime`/`export const dynamic` route-segment config - which `docs/SPEC.md` section 2 explicitly requires on every route handler - a build error ("not compatible with nextConfig.cacheComponents"). Turning it off restores the traditional, spec-compliant route config instead of redesigning every route around the newer caching model. (2026-10-24)

- **Live CLI verification (complete guides for Linear, Zoom, and an unfamiliar app from `npm run research`) is pending, not done, as of this commit.** Both providers' free tiers are exhausted from this session's own testing: Groq's `openai/gpt-oss-120b` daily token budget (200,000 TPD) is used up (confirmed via repeated live runs, not a code bug - the pipeline mechanically completed resolve, discover [including its JSON-repair fallback], and probe correctly before hitting the 429 on the draft stage), and Gemini's `googleSearch`/`urlContext` grounding tools are separately `RESOURCE_EXHAUSTED`. The code itself is finished and covered by unit tests that mock every provider call (discover's parallel-call merge/dedupe/id-assignment, its JSON-repair path, its Gemini-fails-twice-so-fall-back-to-Groq path; draft's Groq-strict-then-Gemini-JSON-mode fallback; check's batching, provider fallback, and 40-claim cap; finalize's full assembly including the customerAdmin override). **Before Phase 2 is actually gated closed, run `npm run research -- "<app>"` against Linear, Zoom, and one unfamiliar app (e.g. Calendly) once quota resets, and confirm a stage timing log shows the whole run finishing under `RESEARCH_DEADLINE_SECONDS`.** (2026-10-24)

## Phase 3

- **Each of the 9 library guides' "Scopes" section now lists real, named scopes (not generic categories), fetched by hand from each provider's own scope/permission reference** (HubSpot `/docs/.../scopes`, Zoom `/docs/integrations/oauth-scopes/`, Slack `/reference/scopes`, Notion `/reference/capabilities`, Linear's OAuth doc, Microsoft Graph's permissions reference, Gmail's scope reference, LinkedIn's Marketing API permissions table). User explicitly asked for this after reviewing the HubSpot doc and finding the generic "Required scopes" / "Optional scopes" rows unhelpful. Per `AskUserQuestion`, chose a **curated common set (~15-25 scopes)** per app over the full raw catalog (HubSpot alone documents 200+): enough to be genuinely useful without turning the table into noise. Exceptions: Notion (8) and Linear (6) because those are each provider's *entire* scope/capability catalog; Gong (6) because its fuller catalog sits behind an authenticated dashboard the agent cannot sign into (`CLAUDE.md`'s "agent reads public web pages only" rule), so only the handful of scope names public docs expose are shown, with the rest honestly marked unknown rather than invented. (2026-10-25)
- **Several providers' scope-reference pages (HubSpot, Slack, Notion) render their actual scope table client-side in JS, so the deterministic `probeFindings()` fetch (plain HTTP GET, no JS execution) never sees the table text and the excerpt/mustContain check always reports a mismatch.** Confirmed directly (fetched the same URL both ways: a plain fetch gets the full page including the table in a browser, but `safeFetch` + `htmlToText` returns only ~5K chars of nav/intro boilerplate for these specific pages). This is a genuine, structural limitation, not a bug to patch around with a different User-Agent or parser tweak. Handling: each such app's scopes array keeps one general "mechanics" row citing an already-passing finding (so the section isn't flagged thin), while the specific named-scope rows cite only the scopes-page finding and are correctly labeled Uncertain by `evidence.ts` - code-decided, consistent with every other Uncertain claim already in these files, not a special case. Zoom, Gong, Linear, Microsoft Teams, Google (Gmail), and LinkedIn's scope-reference pages *do* render server-side, so their named-scope claims passed the real probe and are legitimately labeled Tested/Sourced. (2026-10-25)
- **Rewrote the Zoom, HubSpot, and Microsoft Teams review docs a second time** after the user's follow-up feedback on the first simplified rewrite: dropped reviewer-directed parenthetical asides (e.g. "worth checking against your own experience") entirely rather than softening them, and replaced the bare "Tier N" label with a one-paragraph plain-language explanation of what that tier's review actually involves, before any numbers. (2026-10-25)

- **`groqBrowserSearch`'s `max_completion_tokens` raised from 4000 to 8000.** A live Zoom generation showed the community discover call spend 57,933 total tokens (mostly the tool's own internal search/visit rounds) and still get its final JSON answer cut off mid-stream at the 4000-token cap, producing unparseable output that even the repair call couldn't recover (it legitimately had no complete findings to extract). 8000 gives the model room to finish writing its JSON after browsing. (2026-10-24)
- **Library generation is blocked on the same exhausted Groq/Gemini free-tier quota as Phase 2's live verification**, confirmed again live: a single successful `discover-community` call for Zoom used ~58k of the ~200k daily token budget by itself, so generating all 9 library guides (2 discover calls + 2 draft calls + up to 2 check calls each) will need either a much larger daily budget, several days spread out, or a paid tier. `scripts/library-generate.ts`, `scripts/library-validate.ts`, and `scripts/library-links.ts` are written and type-checked but have not yet produced a real `content/library/drafts/*.json` file. (2026-10-24)

- **Provider base URLs verified live** against console.groq.com and ai.google.dev on 2026-10-24 rather than assumed from `docs/SPEC.md`/`.env.example` alone, at the user's request. Both matched the documented defaults exactly: Groq `https://api.groq.com/openai/v1`, Gemini OpenAI-compatible fallback `https://generativelanguage.googleapis.com/v1beta/openai/`. (2026-10-24)
- **`IP_HASH_SALT` generated automatically** (64 random hex chars written directly into `.env.local`) instead of asking the user to supply one: `.env.example` only asks for "any long random string," it is not a provider credential, and it never needs to be typed in chat or read back. (2026-10-24)

The user chose to fall back to Groq for both stages rather than wait. The Gemini key itself is valid (model listing succeeds) so this can be revisited later by switching these two vars back to `gemini`. (2026-10-24)
- **`GEMINI_MODEL_RESEARCH`/`GEMINI_MODEL_CHECK` set to `gemini-flash-latest`**: `gemini-2.5-flash` (the model named in `.env.example`'s comment) now returns `404` for new users; Google's error message points to the evergreen alias. (2026-10-24)
- **`GROQ_MODEL_FAST` set to `openai/gpt-oss-20b`** (not `llama-3.3-70b-versatile`, which `check-keys` showed as `404` - not on this account/no longer offered): this account's `models.list` only returns 11 models, mostly audio/safety/embedding models plus `allam-2-7b`, `openai/gpt-oss-20b`, `openai/gpt-oss-120b`, `qwen/qwen3.8-27b`. `.env.example`'s default was updated to match. (2026-10-24)
- **Reverted `PROVIDER_RESEARCH`/`PROVIDER_CHECK` from `groq` back to the `gemini` default, and switched `discover.ts`'s `browser_search` calls from `GROQ_MODEL_DRAFT` (`openai/gpt-oss-120b`) to `GROQ_MODEL_FAST` (`openai/gpt-oss-20b`).** Root-caused why live research ("Check an app") stopped working entirely late in the same day Groq-only routing was adopted: Groq's `browser_search` is an opaque, server-side agentic tool with no documented parameter to cap its internal search/visit loop (confirmed via Groq's own docs - `max_completion_tokens` only bounds the final answer, not the tool's internal rounds), and a single `discover()` call makes it run *twice in parallel* (official + community sources). One observed call alone used 57,933 tokens; two in parallel plus the draft/check stages on top can burn 50-70%+ of the entire 200,000 TPD Groq budget in a single research run. Worse, Groq's daily limit turned out to be a rolling 24h window, not a fixed midnight reset (confirmed: `check-keys` kept returning "try again in N minutes" at all times of day, never "try again at UTC midnight"), so once exhausted it only trickles back a little at a time rather than resetting at a predictable hour. Fix: route research/check back through Gemini (a separate quota, not shared with Groq - the original default, before the earlier Gemini-outage workaround above), falling back to Groq only on a Gemini failure as already designed, and use the cheaper/smaller Groq model for the browser_search fallback path specifically (draftCore/draftPath keep `GROQ_MODEL_DRAFT` since strict-json-schema quality matters more there and that call doesn't run an open-ended tool loop). Also softened the three `provider_busy` error messages in `pipeline.ts` from "try again shortly" (misleading when the real wait can be hours) to "try again in a while, or browse the reviewed library below." (2026-10-25)
- **`groq/compound` is retired** (Groq decommissioned it and `groq/compound-mini` on 2026-09-21; `check-keys` got `404`). Groq's current web-search path is the `browser_search` built-in tool (`tools: [{type: 'browser_search'}]`, `tool_choice: 'required'`) on a `gpt-oss` model (`openai/gpt-oss-20b`, `openai/gpt-oss-120b`, or `openai/gpt-oss-safeguard-20b`) - confirmed working on `openai/gpt-oss-120b` with this key. **This changes the Phase 2 research pipeline**: the Groq research-fallback path in `docs/SPEC.md` section 8 (step 2, "Fallback if `PROVIDER_RESEARCH=groq`") must call `GROQ_MODEL_DRAFT` (or `GROQ_MODEL_FAST`) with the `browser_search` tool instead of a separate `GROQ_MODEL_COMPOUND` model id. `GROQ_MODEL_COMPOUND` is kept in `.env.example` as a harmless unused placeholder rather than removed, in case Groq reintroduces a dedicated compound model later; `check-keys.ts` no longer tests it and tests `browser_search` instead. Flag for Phase 2: `browser_search` is documented as incompatible with structured outputs, so the discover stage's JSON-parsing approach (parse a fenced block from reply text) remains necessary rather than switching to strict mode when this tool is active. (2026-10-24)
